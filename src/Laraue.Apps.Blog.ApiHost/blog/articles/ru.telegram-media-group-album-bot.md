> **Architecture First: как в одиночку с ИИ сделать альтернативу Jira** — Часть 12.
> [Предыдущая статья](telegram-bot-file-storage-stream) научила бота захватывать медиа и оставила один болтающийся хвост: захваченное сообщение не заморожено. Люди правят то, что отправили, и шлют альбомы. Эта статья разбирается с обоими случаями.

Флоу захвата до сих пор предполагал, что сообщение приходит один раз, и никогда не меняется. Реальное использование Telegram вносит коррективы в обе части этого допущения. Люди правят сообщение после отправки — исправляют опечатку, добавляют строчку, — и шлют несколько фото разом альбомом, который Telegram доставляет не одним сообщением, а пачкой отдельных. Система захвата, игнорирующая любой из этих случаев, делает не то: создаёт дубль-карточку на правку или разбрасывает один альбом по нескольким карточкам. Эта статья — про то, как сделать оба случая правильно, и второй по-настоящему неудобен — настолько, что привычный ответ тянется к таймеру в памяти, которого этой реализации удаётся избежать.

## Правка — это не новое сообщение

Начнём с половины попроще. Когда кто-то правит сообщение, уже отправленное боту, Telegram доставляет апдейт *отредактированного сообщения* — и бот должен распознать его как изменение чего-то уже сохранённого, а не как совершенно новый захват.

Фундамент под это был заложен ещё в миддлваре из [прошлой статьи](telegram-bot-file-storage-stream) ([`HandleAllMessagesMiddleware`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.TelegramHost/HandleAllMessagesMiddleware.cs)), который разрешает два типа апдейтов, а не один:

```csharp
private static readonly UpdateType[] AllowedUpdates =
[
    UpdateType.Message,
    UpdateType.EditedMessage,
];
```

и читает тот, что пришёл:

```csharp
var message = context.Update.Message ?? context.Update.EditedMessage;
```

То есть новые и отредактированные сообщения идут через *ровно один и тот же* путь маппинга и сохранения — отредактированное фото всё так же маппится через `GetPhotoRequest`, отредактированный текст — через `GetMessageRequest`, и так далее. Миддлвар не ветвится на «это правка или нет»; он обрабатывает оба случая единообразно и оставляет save-сервису разбираться, новое ли пришло или изменение. Это намеренно: решение «новое против обновления» принадлежит коду, который реально может заглянуть в базу и проверить, а не коду, читающему тип апдейта. Тип апдейта говорит, что Telegram *называет* это правкой; только поиск в базе говорит, есть ли это уже *у тебя*.

## Обнови карточку, а не создавай новую

Случай одиночного сообщения — это место, где живёт логика «создать или обновить». Прежде чем что-либо делать, save-сервис ищет существующую запись по внешней идентичности сообщения — id сообщения Telegram плюс чат, из которого оно пришло:

```csharp
var savedMessage = await context.TelegramMessages
    .Where(x => x.ExternalMessageId == request.ExternalMessageId)
    .Where(x => x.ExternalChatId == request.ExternalUserId)
    .Select(x => new
    {
        IssueId = x.Issue != null ? (long?)x.Issue.Id : null,
        x.Id,
    })
    .FirstOrDefaultAsync(cancellationToken);
```

Дальше логика развилки зависит от того, существует ли уже карточка для этого сообщения. Если сохранённого сообщения ещё нет или к нему не привязана issue, это настоящий новый захват: при необходимости создаётся строка сообщения, а внутри транзакции создаётся карточка, и возвращается результат `MainMessageCreated`.

```csharp
if (savedMessage?.IssueId is null)
{
    var statusId = await GetStatusIdToSaveMessage(request.UserId, cancellationToken);

    await using var transaction = await context.Database
        .BeginTransactionAsync(cancellationToken);

    // create the TelegramMessage row if it does not exist,
    // then create the issue/card for it
    await coreIssuesService.Create(
        new CreateIssueRequest
        {
            CreatedAt = request.SentAt,
            Text = request.Text,
            TelegramMessageId = messageId,
            StatusId = statusId,
            UserId = request.UserId,
        }, cancellationToken);

    await transaction.CommitAsync(cancellationToken);

    return new GetOrCreateMessageResult
    {
        Result = Result.MainMessageCreated,
        TelegramMessageId = messageId
    };
}
```

Но если сообщение уже на месте и у него уже есть карточка, запрос — это *правка* чего-то захваченного раньше. Новой карточки нет; содержимое существующей обновляется на месте:

```csharp
await context.Issues
    .Where(x => x.TelegramMessageId == savedMessage.Id)
    .ExecuteUpdateAsync(upd => upd
        .SetProperty(x => x.Content, request.Text),
        cancellationToken);

return new GetOrCreateMessageResult
{
    Result = Result.MainMessageUpdated,
    TelegramMessageId = savedMessage.Id,
};
```

Вот и весь механизм правки для одиночного сообщения: найти его и либо создать карточку, либо обновить ту, что есть. `ExecuteUpdateAsync` пишет новый текст прямо в существующую карточку, не загружая и не пересохраняя сущность. (`GetStatusIdToSaveMessage` определяет место по умолчанию, куда попадает свежезахваченное сообщение; детали того, как этот дефолт выбирается, относятся к более поздней статье и здесь опущены.) Важно то, какой результат метод возвращает — `MainMessageCreated` или `MainMessageUpdated`, — потому что именно это видит пользователь.

Стоит точно сказать, что на самом деле означает `MainMessageUpdated`, потому что это шире, чем «правка». Это значит, что *сообщение присоединилось к карточке, которая уже существовала*, а не создало новую, — и это случается в двух разных ситуациях. Одна — настоящая правка, как выше. Другая — второе, третье и последующие фото альбома: как объясняет следующий раздел, Telegram шлёт каждое изображение многофотного сообщения *отдельным* сообщением, и слить их в одну карточку — задача бэкенда. Эти последующие части — не правки ни в каком пользовательском смысле, но механически они идут тем же путём: находят существующую карточку и присоединяются к ней, а не создают новую. Так что `MainMessageUpdated` — это на самом деле «влилось во что-то, что уже было», независимо от того, было ли это что-то создано мгновение назад первым фото того же альбома или вчера сообщением, которое пользователь только что отредактировал. Единый механизм «создать или обновить» обрабатывает оба случая — отчасти поэтому он построен вокруг поиска в базе, а не вокруг типа апдейта.

## Реакция сообщает пользователю, что произошло

Флоу захвата даёт пользователю ровно один кусочек фидбэка, и он молчаливый: реакция на его собственное сообщение. Слой оркестрации выставляет её по результату, который вернуло сохранение:

```csharp
var result = await saveMessageService.Save(request, cancellationToken);

if (result.Result is Result.MainMessageCreated)
    await SetReaction(request, "👍", cancellationToken);
else if (result.Result is Result.MainMessageUpdated)
    await SetReaction(request, "❤", cancellationToken);
```

Захват, создавший новую карточку, получает 👍; влившийся в существующую — ❤, независимо от того, была ли это правка или последующая часть альбома. Эта разница — вся видимая пользователю поверхность этой фичи: никакого сообщения «обновлено!», никакого диалога подтверждения, ничего, что надо закрывать. Пользователь правит своё сообщение и видит, как реакция тихо оседает на сердечке, — этого достаточно, чтобы понять, что система заметила. Это держит обещание без трения из [урока про «Избранное»](telegram-saved-messages-bot-lesson): бот подтверждает, но не перебивает. Само выставление реакции — это один вызов Bot API:

```csharp
private async Task SetReaction(
    SaveMessageTelegramRequest request,
    string? reaction,
    CancellationToken ct)
{
    await client.SetMessageReaction(
        request.ExternalUserId,
        request.ExternalMessageId,
        reaction is not null
            ? [new ReactionTypeEmoji { Emoji = reaction }]
            : [],
        cancellationToken: ct);
}
```

Была здесь и заманчивая идея, не пережившая столкновения с API: менять реакцию на *каждую* правку, чтобы повторные правки наглядно перебирали разные эмодзи. Telegram не предлагает способа прочитать текущий набор реакций сообщения, так что для этого пришлось бы хранить текущий эмодзи каждого сообщения самим — чисто чтобы знать, на что менять дальше. Это реальное состояние, которое надо поддерживать ради косметической детали, поэтому фича остаётся в двух состояниях — создано и обновлено, — которым не нужна сохранённая история, потому что результат сохранения и так говорит, какое из них применимо. Маленький пример того, как ограничение API отговаривает тебя от фичи, которая и так не стоила своей цены.

## Сложный случай: медиагруппы

Теперь неудобная половина. Когда пользователь шлёт несколько фото разом альбомом, Telegram не доставляет одно сообщение с несколькими фото. Он доставляет *несколько отдельных сообщений*, у которых общий **media group id**, приходящих быстрой пачкой без гарантированного порядка. Собрать эту пачку обратно в одну карточку — самый трудный кусок логики захвата, и обрабатывается он в отдельном методе [`SaveGroupMessageEntity`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.TelegramServices/Services/Messages/TelegramSaveMessageService.cs) — остаток этого раздела описывает его форму, а не проходит по каждой строке, потому что построчные детали есть в исходнике.

Суть проблемы — рассогласование в счёте. Для пользователя альбом — это одна вещь, которую он отправил. Для Telegram — это N сообщений. Для приложения это должна быть одна карточка с N вложениями. Поэтому save-сервис маршрутизирует групповые сообщения иначе, чем одиночные:

```csharp
private Task<GetOrCreateMessageResult> SaveMessageEntity(
    SaveMessageTelegramRequest request,
    CancellationToken cancellationToken)
{
    return request.MediaGroupId == null
        ? SaveSingleMessageEntity(request, cancellationToken)
        : SaveGroupMessageEntity(request, cancellationToken);
}
```

Распространённое решение этой проблемы, то, что находишь на форумах большинства бот-фреймворков, — **таймер-аккумулятор**: когда приходит сообщение с media group id, буферизуешь его в памяти, запускаешь (или сбрасываешь) короткий таймер, и когда таймер наконец срабатывает без прихода новых частей, считаешь альбом завершённым и обрабатываешь весь буфер разом. Это работает, но хрупко так, как это важно. Оно держит состояние в памяти, так что перезапуск посреди альбома теряет уже пришедшие части. Таймер — это догадка: слишком короткий — и ты разбиваешь один альбом на несколько, слишком длинный — и каждый альбом ощущается тормозным. И оно предполагает, что все части приходят близко друг к другу, что обычно, но не всегда верно.

Эта реализация избегает таймера целиком, опираясь на базу вместо памяти. Шага «подождать, пока альбом закончится» нет вовсе; каждая часть обрабатывается по мере прихода, а связывает их слой персистентности. В основе — несколько идей. Во-первых, медиагруппа получает собственную строку в базе, создаваемую один раз и переиспользуемую, чтобы все отдельные сообщения одного альбома можно было привязать к единой групповой идентичности — это и делает `GetOrCreateTelegramMediaGroupId`: ищет группу по её Telegram-id, создаёт, если это первая пришедшая часть, и возвращает иначе. Во-вторых, правило, какое сообщение владеет карточкой: **только первое сообщение группы несёт содержимое и создаёт карточку.** Последующие части альбома не создают каждая свою карточку; они находят существующую карточку группы и присоединяют к ней своё медиа. Поскольку части приходят без фиксированного порядка, «первое» определяется запросом сохранённых сообщений группы с сортировкой, а не доверием к порядку прихода или таймеру. Поскольку всё это живёт в базе, а не в буфере в памяти, перезапуск посреди альбома не теряет ничего — уже обработанные части сохранены, а те, что ещё идут, их найдут.

Остаются пограничные случаи — вот где становится по-настоящему муторно и где код несёт честные `TODO`. Один реальный пример, обработанный в коде: первое сообщение группы — то, что держало текстовое содержимое, — удаляют, а текст пользователь добавляет к другой части. Теперь часть, которая должна владеть карточкой, больше не существует, а содержимое переехало. Код это обнаруживает и обновляет содержимое уцелевшей карточки из той части, у которой теперь есть текст:

```csharp
// The case when first message was deleted and text added to the second
if (request.Text is not null && firstGroupMessageData is not null)
{
    // TODO - here we can detect and remove previous messages. But should we?
    await context.Issues
        .Where(x => x.Id == firstGroupMessageData.CardId)
        .ExecuteUpdateAsync(upd => upd
                .SetProperty(x => x.Content, request.Text),
            cancellationToken);
    // ...
}
```

`TODO` честен насчёт предела: здесь есть более глубокие вопросы согласованности («стоит ли обнаруживать и удалять предыдущие сообщения?»), которые отмечены, но не решены, потому что случаи, их запускающие, редки, а цена обработки каждого высока. Путь альбома хорошо обрабатывает распространённые формы и помечает экзотические для «когда-нибудь», которое может и не понадобиться.

## То, чего бот не может: удаления

Правки бот видит. Удаления — нет. Telegram не доставляет боту апдейт, когда пользователь удаляет сообщение из своего чата, — события для этого просто нет, — так что у бота нет способа узнать, что нечто им захваченное было удалено на стороне Telegram. В результате удаление захваченной карточки поддерживается только из веб-интерфейса, а не из чата.

Стоит задуматься, *почему* Telegram не шлёт это событие, потому что неоднозначность тут оказывается настоящей, а не недосмотром. Подумайте, что должно произойти, когда пользователь удаляет всю историю чата с ботом. Должно ли это выстрелить удаление по каждому сообщению, стерев всё, что он когда-либо захватил? Почти наверняка он имел в виду не это — очистить чат это жест уборки чата, а не «уничтожь все мои сохранённые задачи». Но и противоположный дефолт — игнорировать — тоже защитим. Нет прочтения «пользователь удалил это сообщение», которое было бы однозначно верным для системы, захватившей сообщение во что-то более долговечное, поэтому Telegram отказывается гадать. С учётом этого делать удаление в веб-приложении — где «удалить эту карточку» означает ровно и только это — и есть правильное для него место.

Есть возможная будущая золотая середина: явный жест в чате, однозначный *потому что* его выбрал пользователь, — например, реакция на захваченное сообщение определённым эмодзи, чтобы сказать боту удалить соответствующую карточку. Это сохраняет удаление доступным в чате, не наследуя неоднозначности сырого удаления сообщений, потому что пользователь намеренно сигнализирует о намерении, а не бот гадает по отсутствию. Удобно ли это на деле — открытый вопрос: реакция-на-удаление из тех штук, что звучат изящно, а на практике могут ощущаться неуклюже, — так что пока это остаётся идеей, а не фичей.

## Почему это муторно и чему учит

Причина, по которой эта статья существует, в том, что модель сообщения у Telegram и модель захваченной карточки у приложения не совпадают. Telegram говорит, что правка — это новый апдейт; приложению нужно, чтобы это было изменение существующей карточки. Telegram говорит, что альбом — это пачка отдельных сообщений; приложению нужно, чтобы это была одна карточка. Telegram не говорит вообще ничего, когда сообщение удаляют; приложению приходится жить с этим молчанием. Save-сервис — это шов, где это рассогласование примиряется, где грязная внешняя реальность того, как Telegram доставляет вещи, переводится в чистую внутреннюю реальность, которую остальное приложение может принимать как данность.

Это та же тема, что и маппинг-миддлвар из прошлой статьи, где анимация и видео схлопнулись в один концепт приложения. Здесь это правки и альбомы, схлопывающиеся в «создать или обновить карточку». В обоих случаях дисциплина одна: делать примирение *на границе*, в одном месте, чтобы всё ниже по течению работало с простой моделью и никогда не знало, насколько нерегулярным был ввод. Цена в том, что это одно место не простое — save-сервис самый замысловатый код в боте именно потому, что он впитывает всю нерегулярность, чтобы ничему другому не пришлось.

И он отгружен прагматично, а не идеально. Обработка медиагрупп имеет шероховатости и помеченные `TODO`; распространённые случаи работают, редкие — отмечены. Это снова решение по масштабу: обрабатывай то, что реальные пользователи действительно делают, и не трать дни на закаливание путей, по которым почти никто не пойдёт, когда эти дни могут построить то, чем люди воспользуются.

## К чему мы пришли

Бот теперь справляется со всей реальностью того, как люди на самом деле ему отправляют: текст и медиа, отправленные единожды или отредактированные позже, по одному за раз или альбомом. Ничто из этого не изменило опыт *использования* бота — захват по-прежнему «отправил и забыл», единственный фидбэк — тихая реакция, которая теперь различает новое сохранение и правку. Вся сложность ушла туда, где сложности и место: на сервер, на границу, невидимо для того, кто отправляет фото. На этом половина продукта про захват — бот — по-настоящему готова. Она делает одно дело, захватывает что угодно, что ты в неё кинешь, и не путается под ногами.

## Что дальше

И вот вопрос, на котором стоит задержаться. Бот закончен, и почти всё интересное дальше живёт в веб-приложении — доски, организация, собственно управление тем, что было захвачено. А работа над ним вскрыла осознание про всю архитектуру: Telegram, при всём том, что это «Telegram-native» продукт, по-настоящему нужен лишь для одного — для логина. Почти всё остальное, что делает приложение, могло бы работать без Telegram вообще. Следующая статья полностью поворачивается к веб-приложению — и к тому, что значит построить Telegram-продукт, который едва зависит от Telegram.
