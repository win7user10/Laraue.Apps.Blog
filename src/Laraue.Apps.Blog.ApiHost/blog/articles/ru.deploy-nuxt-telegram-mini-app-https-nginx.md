> **Architecture First: как в одиночку с ИИ сделать альтернативу Jira** — Часть 7.
> В [Предыдущей статье](deploying-dotnet-postgres-vps-docker-compose) Telegram бот был развернут на сервере. Бот занимается сохранением сообщений пользователя; этот этап начинает вторую половину продукта — веб-приложение с канбан-досками.

Бот занимается только одной активностью: сохраняет сообщения пользователя в чате как задачи. Всё остальное — отрисовка задач на доске, их передвижение между колонками, в общем весь процесс управления задачами — находится в веб-приложении. Эта статья делает первую его часть: фундамент, на котором будут строиться фичи приложения. Цель этого этапа: добиться, чтобы Nuxt-приложение открывалось внутри Telegram как Mini App.

Порядок работы намеренный. Сначала сделать приложение, пусть даже пустое, наладить его деплой на сервер и увидеть объект пользователя, который отдаёт Telegram. Потом сделать его доступным по HTTPS — поддомен, обратный прокси, сертификат, — потому что у Telegram Mini App есть одно жёсткое требование. И только в самом конце, когда уже есть реальный HTTPS-URL, раздающий приложение, рассказать о нём Telegram.

## Само приложение: пустой Nuxt-проект, который может определить, что он запущен из Telegram

Фронтенд начался с пустого приложения на [Nuxt](https://nuxt.com/), созданного стартовой командой самого Nuxt, заведённого в собственный репозиторий ([laraue-boards](https://github.com/win7user10/laraue-boards)) и запушенного. Поскольку остальной тулчейн здесь использует pnpm, проект создан pnpm-формой официальной команды:

```bash
pnpm create nuxt@latest laraue-boards
```

Это даёт минимальный, запускаемый Nuxt-проект — никаких фич, компонентов, доски, только фреймворк и `app.vue`. Всё в этой статье строится поверх этой отправной точки.

Единственное, что первой версии и правда было нужно, — способ понять, *как* её открыли. Mini App запускается внутри Telegram, где Telegram передаёт ей идентифицирующие данные через свой SDK. Приложению надо прочитать эти данные и превратить их в залогиненного пользователя. Это происходит в Nuxt-плагине [`auth.init.ts`](https://github.com/win7user10/laraue-boards/blob/master/app/plugins/auth.init.ts), который запускается на старте. В первой версии он был настолько маленьким, насколько это вообще возможно:

```ts
export default defineNuxtPlugin(async (nuxtApp) => {
  const { setIsAppInitialized, setIsInMiniApp } = useAppState();
  const { setUser } = useAuth();
  try {
    const WebApp = (await import('@twa-dev/sdk')).default;
    const isInMiniApp = WebApp.initData !== '';
    if (isInMiniApp) {
      setIsInMiniApp(true);
      setUser(WebApp.initData);
    } else {
      throw Error('Init data object is missing');
    }
  } catch (err) {
    const { setInitError } = useAppState();
    setInitError(err);
  } finally {
    setIsAppInitialized(true);
  }
});
```

Ключевая строка — `WebApp.initData !== ''`. Пакет `@twa-dev/sdk` отдаёт данные Mini App от Telegram; когда приложение запущено внутри Telegram, `initData` заполнено, а когда открыто в обычном браузере — пусто. Эта одна проверка и есть то, как приложение решает, реальный ли это запуск Mini App. Если да — плагин это фиксирует и ставит пользователя прямо из init data; если нет — кидает ошибку, и она перехватывается, чтобы экран показал, что пошло не так. В любом случае в конце приложение помечается инициализированным, чтобы UI понял, что можно рендериться.

Стоит честно сказать, насколько минимальной была эта первая версия. Она брала Telegram init data и ставила пользователя прямо из них — **без всякой проверки, что данные действительно валидны**. Не было проверок, что init data подлинные и не подделаны, а это в реальной реализации абсолютно необходимо (Telegram подписывает init data именно для того, чтобы бэкенд мог их проверить); эта валидация появилась позже и относится к следующей статье. Компонентов тоже не было вообще. Весь шаблон `app.vue` существовал только чтобы доказать, что плагин отработал и выдал объект пользователя:

```vue
<template>
  <div id="app">
    <div v-if="initError">
      {{ initError }}
    </div>
    <div v-else>
      {{ appState.user }}
    </div>
  </div>
</template>
```

Это весь UI: если инициализация упала — печатаем ошибку, иначе — объект пользователя. Ни доски, ни стилей, ни навигации. Смысл первой версии был не в том, чтобы на что-то походить, — а в том, чтобы подтвердить, от начала до конца, что приложение грузится, плагин отрабатывает, контекст Mini App определяется, и данные пользователя приходят от Telegram. Как только это стало видно на экране, фундамент был доказан, и поверх него можно было собирать настоящий UI. (Текущий [`app.vue`](https://github.com/win7user10/laraue-boards/blob/master/app/app.vue) делает куда больше, но вырос из этого.)

## Деплоим фронтенд

Когда приложение в репозитории, следующий шаг — доставить его на сервер. У фронтенда свой CI-пайплайн, отдельный от бота, потому что это отдельный репозиторий с совершенно другой сборкой. Там, где пайплайн бота собирает .NET и копирует скомпилированный хост, этот собирает Nuxt-приложение и копирует статический результат:

```yaml
name: Build Vue App
on:
  push:
    branches: [ "master" ]
  pull_request:
    branches: [ "master" ]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 10
      - name: Use Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20.x'
          cache: 'pnpm'
      - run: pnpm i
      - run: pnpm nuxt generate
      - name: Upload
        if: github.ref == 'refs/heads/master'
        uses: marcodallasanta/ssh-scp-deploy@v1.2.0
        with:
          host: ${{ secrets.SSH_HOST }}
          port: ${{ secrets.SSH_PORT }}
          user: ${{ secrets.SSH_USER }}
          password: ${{ secrets.SSH_PASSWORD }}
          local: .output/*
          remote: "/home/laraue/note-to-board-frontend"
          post_upload: echo "Uploaded"
```

Он ставит pnpm и Node, запускает `pnpm nuxt generate` и — только на `master` — копирует результат на сервер по SSH, тем же экшеном `ssh-scp-deploy`, что и пайплайн бота. Паттерн идентичный: собрать в CI, перекинуть результат по SCP в папку под `/home/laraue/` — здесь `note-to-board-frontend`, ровно та папка, которую контейнер nginx смонтирует как свой веб-рут.

Важная деталь — `nuxt generate`, а не `nuxt build`. `generate` пререндерит приложение в полностью статический сайт — обычные HTML, CSS и JavaScript-файлы без серверной части. Именно это и позволяет раздавать приложение файлами из-за nginx, без запущенного Node-процесса, и это то решение на этапе сборки, на котором держится вся схема статического хостинга. (Когда фронтенд позже переедет на серверный рендеринг ради публичных досок, это одна из вещей, что изменится: `generate` станет `build`, а заливка статики — запущенным SSR-хостом.)

На этом этапе собранное приложение лежит на сервере в папке, но наружу его пока ничто не раздаёт. Это следующая задача.

## Поддомен, и почему необходим HTTPS

Приложение собрано и лежит на сервере, но наружу его ничто не раздаёт, и вот здесь одно жёсткое требование Telegram Mini App забирает себе остаток статьи. Telegram не загрузит Mini App по обычному HTTP — URL, который вы регистрируете, должен быть HTTPS, с валидным сертификатом. Это работает везде, без исключений: ни в проде, ни на вашем ноутбуке во время разработки (эта проблема решается дальше через туннель). Боту ничего из этого не было нужно, потому что long polling тянется наружу и никогда не принимает входящее соединение. Веб-приложение — противоположность: оно существует, чтобы до него достучались, а значит, достучаться должны безопасно. Так что дальше работа — это цепочка: поддомен, обратный прокси, сертификат, — и делать её надо именно в таком порядке.

Начинается всё с поддомена. Приложение живёт на собственном поддомене `msgboard.laraue.com`, отдельном от блога на основном домене. Держать его на поддомене, а не на пути под основным сайтом, чисто разделяет зоны ответственности — блог и таск-трекер это разные приложения с разными жизненными циклами деплоя, и граница поддомена это отражает, оставляя при этом настройку TLS и прокси для каждого независимой.

Создаётся поддомен там, где управляется домен, — в DNS- или хостинг-панели регистратора домена. Там вы добавляете одну `A`-запись для `msgboard`, указывающую на IP-адрес VPS, того же сервера, где уже работают бот и блог. Ничего экзотического: ещё одна `A`-запись, нацеленная на сервер.

Единственное, с чем надо запастись терпением, — это распространение записи. Новая DNS-запись не вступает в силу мгновенно — на то, чтобы `A`-запись разошлась и `msgboard.laraue.com` действительно начал резолвиться на сервер, может уйти от нескольких минут до заметно большего времени. Это важно для следующих шагов, потому что **сертификат нельзя выпустить, пока поддомен не резолвится**. Let's Encrypt проверяет владение доменом, подключаясь к нему через публичный интернет, так что если DNS ещё не разошёлся, эта проверка просто падает — с ошибкой, которая прямо называет проблему:

```
DNS problem: NXDOMAIN looking up A for msgboard.laraue.com
  - check that a DNS record exists for this domain;
DNS problem: NXDOMAIN looking up AAAA for msgboard.laraue.com
  - check that a DNS record exists for this domain
```

`NXDOMAIN` значит, что имя пока не резолвится — либо запись только что добавили и она не разошлась, либо она неверна. Практическая последовательность такая: добавить `A`-запись, подождать, пока поддомен начнёт резолвиться на сервер (быстрый `ping` или DNS-запрос это подтвердят), и только потом пытаться выпустить сертификат. Попытка выпустить сертификат до того, как запись зарезолвится, просто выдаёт ошибку выше.

## nginx как обратный прокси

Перед приложением стоит nginx, работающий ещё одним контейнером в том же стеке Docker Compose, что бот и база. Его задача — терминировать TLS (быть тем, кто держит сертификат и говорит по HTTPS с внешним миром) и раздавать приложение за собой.

Вот сервис nginx в Compose:

```yaml
nginx:
  ports:
    - "80:80"
    - "443:443"
  build:
    context: .
    dockerfile: "NginxDockerfile"
  networks:
    - dockerapi-dev
  volumes:
    - ./../letsencrypt:/etc/letsencrypt
    - ./../.well-known/acme-challenge:/.well-known/acme-challenge
    - ./note-to-board-frontend/public:/usr/share/nginx/html/note-to-board-frontend
  command: "/bin/sh -c 'while :; do sleep 6h & wait $${!}; nginx -s reload; done & nginx -g \"daemon off;\"'"
```

На двух из этих volume стоит остановиться, потому что они определяют, как деплоится весь фронтенд.

**Собранные файлы фронтенда монтируются прямо в nginx как volume.** Строка `./note-to-board-frontend/public:/usr/share/nginx/html/note-to-board-frontend` маппит папку собранной статики на хосте — ту же папку, куда заливает CI-пайплайн, — прямо в место, откуда раздаёт nginx. Следствие — приятная часть: когда новая версия фронтенда залита в эту папку, nginx раздаёт её **сразу**. Нет ни `docker-compose build`, ни `docker-compose up -d`, ни перезапуска контейнера ради изменения фронтенда — файлы меняются на диске, и следующий запрос получает новые. По сравнению с ботом, где деплой означает пересборку и пересоздание контейнера, деплой фронтенда — это просто замена файлов. Так что CI-пайплайн из прошлого раздела — это и есть весь деплой: пуш в `master`, сборка заливает, и новый фронтенд живой, а на сервере делать больше нечего.

**`command` держит nginx перезагружающимся по таймеру.** Шелл-цикл перезагружает nginx каждые шесть часов (`nginx -s reload`), пока тот работает на переднем плане. Эта периодическая перезагрузка нужна в основном чтобы nginx подхватывал обновлённые TLS-сертификаты без чьего-либо вмешательства — certbot обновляет файлы сертификата по своему расписанию, а эта перезагрузка заставляет nginx начать использовать новые.

Эта схема со статикой в volume работает сегодня именно потому, что фронтенд Boards статический. Дальше по проекту план — переехать на серверный рендеринг, по причинам, изложенным ещё в [статье про стек](choosing-stack-for-solo-project): если доски когда-нибудь станут публичными, серверный рендеринг — это то, что позволит их содержимому индексироваться и превращаться в органический трафик. Тогда этот подход сменится проксированием на запущенный Nuxt SSR-процесс, ровно так, как блог уже работает на этом сервере. Но такой потребности пока нет, и пока она не пришла, раздавать статику проще, дешевле и быстрее в деплое.

Поддомену нужно два server-блока. Первый слушает порт 80 и делает две вещи: раздаёт ACME-challenge, которым Let's Encrypt проверяет владение доменом (об этом ниже), и редиректит всё остальное на HTTPS:

```nginx
server {
    listen 80;
    server_name msgboard.laraue.com;
    location /.well-known/acme-challenge/ {
        root /.well-known/acme-challenge;
    }
    location / {
        return 301 https://$host$request_uri;
    }
}
```

Второй блок — настоящий: порт 443, TLS и раздача приложения:

```nginx
server {
    listen 443 ssl;
    server_name msgboard.laraue.com;

    ssl_certificate     /etc/letsencrypt/live/msgboard.laraue.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/msgboard.laraue.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;

    root /usr/share/nginx/html/note-to-board-frontend;
    index index.html;

    location /_nuxt {
        expires 1y;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    location / {
        try_files $uri $uri/ /index.html;

        add_header Cache-Control "no-store, must-revalidate";
        add_header Pragma "no-cache";
        add_header Expires 0;
    }

    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|eot|json)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }
}
```

Несколько вещей в этом блоке стоит вытащить наружу.

**`root` указывает на смонтированную статику.** Это другой конец volume из Compose-сервиса выше — nginx раздаёт фронтенд прямо из `/usr/share/nginx/html/note-to-board-frontend`, собранных файлов, примонтированных с хоста. Ни сервера приложения, ни Node-процесса; просто файлы на диске.

**Строка `try_files ... /index.html` — это SPA-fallback.** SPA само занимается своим роутингом в браузере, так что когда кто-то переходит на клиентский роут, nginx не должен возвращать 404 — он должен отдать `index.html` и дать роутеру приложения взять управление. Эта одна строка и есть то, что заставляет работать глубокие ссылки и навигацию внутри приложения.

**Кеширование намеренно разделено.** Сборка Nuxt под `/_nuxt` и статика вроде JS, CSS и картинок имеют хеш в имени — их имена меняются, когда меняется содержимое, — поэтому они помечены `immutable` и кешируются на год. А вот сам `index.html` помечен `no-store, must-revalidate`, так что браузер всегда тянет свежую копию. Это стандартный паттерн кеширования для SPA: кешировать хешированную статику навсегда, никогда не кешировать точку входа, и тогда деплой подхватывается мгновенно, без раздачи устаревшего кода.

(В реальном конфиге есть ещё `location`-блоки, которые проксируют роуты `/api/...` на web API. Они относятся к следующей статье, где web API и строится, так что здесь опущены — на этом этапе у приложения ещё нет бэкенда, к которому обращаться.)

## TLS-сертификаты через Let's Encrypt и certbot

Сам сертификат приходит от Let's Encrypt — бесплатного автоматического центра сертификации, выпускается и обновляется через certbot. Бесплатный — ключевое слово: в духе остальных инфраструктурных решений этого проекта, нет причин платить за сертификат, когда автоматический, повсеместно доверенный и бесплатный делает ровно ту же работу.

certbot работает своим контейнером в том же стеке Compose, и вся его задача — держать сертификаты обновлёнными:

```yaml
certbot:
  image: certbot/certbot:v1.7.0
  networks:
    - dockerapi-dev
  volumes:
    - ./../letsencrypt:/etc/letsencrypt
    - ./../.well-known/acme-challenge:/var/www/certbot
  entrypoint: "/bin/sh -c 'trap exit TERM; while :; do certbot renew; sleep 12h & wait $${!}; done;'"
```

Два volume — это вся история того, как это связано с nginx. Первый, `letsencrypt`, — это куда certbot пишет выпущенные сертификаты; на хосте это `/home/letsencrypt`, и nginx читает из той же директории, поэтому пути `ssl_certificate` в server-блоках выше указывают на `/etc/letsencrypt/live/msgboard.laraue.com/`. certbot пишет туда; nginx читает оттуда; папка у них общая. Второй volume, директория `acme-challenge`, — общее пространство, которым Let's Encrypt проверяет, что мы действительно владеем доменом.

Эта проверка и есть ACME-challenge, ради которого был настроен server-блок на порту 80. Чтобы выпустить сертификат для `msgboard.laraue.com`, Let's Encrypt просит сервер доказать, что тот контролирует домен, положив определённый файл под `/.well-known/acme-challenge/` и забрав его по обычному HTTP. Именно поэтому блок порта 80 раздаёт этот путь напрямую, а не редиректит его на HTTPS — challenge должен отработать до того, как появится хоть какой-то сертификат. Как только файл забран и проверен, сертификат выпускается.

`entrypoint` — это то, что делает обновление беспроблемным. Это крошечный шелл-цикл: запустить `certbot renew`, поспать двенадцать часов, и так по кругу, бесконечно. Сертификаты Let's Encrypt живут девяносто дней, а `certbot renew` реально обновляет сертификат только когда тот близок к истечению, так что запускать его дважды в день безвредно и означает, что сертификат всегда обновляется задолго до того, как протухнет. Никакого cron на хосте, никакого напоминания в календаре, никакого ручного шага обновления — контейнер крутится сам, пока работает стек.

Одного этот цикл *не* делает — не получает сертификат в первый раз. `certbot renew` обновляет только уже существующие сертификаты; самый первый выпуск для нового домена надо бутстрапить отдельно.

### Проблема курицы и яйца: nginx не стартует без сертификата

У первого выпуска есть настоящая проблема с порядком, которую стоит понимать, потому что на ней легко споткнуться.

Проблема такая: server-блок на порту 443 ссылается на файлы сертификата через `ssl_certificate` и `ssl_certificate_key`. Если этих файлов нет, **nginx отказывается стартовать** — он не поднимет TLS-сервер, указывающий на отсутствующий сертификат. Но сертификат нельзя получить, пока nginx не запущен и не раздаёт ACME-challenge. nginx нужен сертификат, чтобы стартовать; сертификату нужен запущенный nginx, чтобы выпуститься. Ни один не может пойти первым.

Первоначальный сертификат получают однократным запуском широко используемого скрипта [`init-letsencrypt.sh`](https://github.com/wmnnd/nginx-certbot/blob/master/init-letsencrypt.sh), запускаемого локально против сервера, который разрывает этот тупик в определённом порядке:

1. Он создаёт **заглушку — самоподписанный сертификат** по пути, который ждёт nginx, чтобы файлы сертификата существовали, пусть и поддельные.
2. С этими файлами на месте nginx теперь может **стартовать** — поднимаются и блок порта 80 (раздающий ACME-challenge), и блок порта 443 (с заглушкой-сертификатом).
3. Затем он **удаляет заглушку и запрашивает настоящий** сертификат у Let's Encrypt, который достукивается до запущенного nginx по порту 80, проходит ACME-challenge и выпускает настоящий сертификат.
4. Он **перезагружает nginx**, который теперь подхватывает настоящий сертификат вместо заглушки.

Шаг с заглушкой-сертификатом — это и есть весь фокус: он позволяет nginx стартовать, чтобы можно было получить настоящий сертификат, после чего поддельный выбрасывается. (Это ещё и причина, по которой поддомен должен сначала резолвиться — шаг 3 падает с ошибкой `NXDOMAIN` из начала статьи, если DNS не разошёлся.) После этого бутстрапа контейнер обновления берёт дело на себя, и сертификат больше никогда не требует ручного внимания. Настроил один раз — обновляется бесконечно.

На этом этапе приложение живое: собрано, задеплоено на сервер, раздаётся nginx по HTTPS на `msgboard.laraue.com`, с валидным самообновляющимся сертификатом. Открытие этого URL в обычном браузере показывает болванку-приложение. Всё на месте, кроме одного шага, который делает его Mini App.

## Тестируем Mini App локально через ngrok

Перед этим финальным шагом — пара слов о локальной разработке, потому что требование HTTPS никуда не девается на вашем ноутбуке. Telegram всё так же отказывается открывать Mini App с `http://localhost:3000`, и нельзя указать ему URL, который существует только на вашей машине.

Ответ — [ngrok](https://ngrok.com/), который создаёт публичный HTTPS-URL, туннелирующий на порт вашей локальной машины. С ним фронтенд, запущенный локально на порту 3000, получает публичный адрес `https://...ngrok-free.app`, который Telegram готов загрузить. Полная настройка — в [README](https://github.com/win7user10/laraue-boards) репозитория фронтенда, но в общих чертах это так:

1. **Затуннелить локальные порты.** Конфиг `ngrok.yml` выставляет и фронтенд (3000), и бэкенд (5200) как публичные HTTPS-URL, запускается через `ngrok start --all`.
2. **Навести бота на туннель.** В настройках Mini App в BotFather кнопка Main App ставится на ngrok-URL фронтенда вместо продового поддомена — так открытие Mini App в вашем боте грузит запущенное на ноутбуке приложение.
3. **Дать бэкенду принять туннель.** ngrok-URL фронтенда добавляется в CORS-allowlist бэкенда, а базовый адрес API фронтенда наводится на ngrok-URL бэкенда.

Этого достаточно, чтобы прогнать весь реальный флоу аутентификации — настоящее рукопожатие Telegram Mini App — против кода, запущенного и остановленного на брейкпоинтах на вашей собственной машине.

Есть и шорткат для случаев, когда тестировать саму аутентификацию не нужно. Приложение поддерживает режим преавторизованного пользователя: задайте тестовый токен пользователя в `.env` фронтенда, и приложение запускается как известный пользователь вообще без рукопожатия с Telegram. Это быстрый путь для повседневной работы над UI; маршрут через ngrok — для случаев, когда тестируется сам флоу аутентификации. (Здесь всплывает одна маленькая, но легко цепляемая деталь — бэкенд должен разрешить ngrok-origin в CORS, иначе его ответы возвращаются пустыми внутри Telegram. Этот класс проблем «CORS падает только внутри Telegram» — ровно то, на что следующая статья натыкается в проде.)

Полезный трюк из той же настройки, для всех, кто пытался дебажить пустой экран Mini App: внутри Telegram нет видимой консоли браузера. Инъекция скрипта `eruda` в приложение даёт кнопку экранной консоли прямо внутри Mini App, что превращает «оно просто показывает пустой экран, и я понятия не имею почему» в нечто, что можно реально осмотреть.

## Финальный шаг: регистрируем Mini App в BotFather

Теперь всё на месте — приложение собрано, задеплоено и раздаётся по HTTPS на `msgboard.laraue.com`. Последнее, что осталось, — сказать Telegram, что этот URL и есть Mini App бота. Это делается в BotFather, том же боте, что выдал токен в прошлой статье.

Откройте чат с [@BotFather](https://t.me/BotFather) и выберите своего бота. В разделе **Mini Apps** Telegram предлагает пару способов запускать Mini App: привязав к **menu button** бота (кнопке рядом с полем ввода) или как **Main App**. В любом случае шаг, который имеет значение, — отдать Telegram **URL** Mini App: `https://msgboard.laraue.com`. У Boards Mini App привязана к menu button.

Как только это задано, у бота появляется кнопка запуска. В списке чатов чат с ботом теперь показывает кнопку, чтобы открыть приложение, прямо рядом с собой:

![Кнопка запуска Mini App рядом с чатом бота](https://laraue.com/static/images/blog/articles/laraue-boards/message-board-bot-launch-mini-app-button.jpg)

Нажатие этой кнопки — момент, когда всё в этой статье сходится воедино. Nuxt-приложение открывается панелью над чатом, безопасно раздаётся с поддомена, плагин `auth.init.ts` отрабатывает, читает Telegram init data, и — если всё подключено правильно — экран показывает объект пользователя, который вернулся. Если что-то по пути пошло не так, он показывает init-ошибку вместо этого. Этот голый вывод — объект пользователя или ошибка — ровно то, что минимальная первая версия и была сделана показывать: доказательство, что нажатие внутри Telegram проходит весь путь через HTTPS, nginx, статическое приложение и плагин, и выдаёт реального пользователя Telegram.

Это ещё и причина, по которой URL должен был существовать и быть HTTPS *до* этого шага: BotFather регистрирует реальный, достижимый адрес, а Telegram загрузит только HTTPS. Делать это последним, после того как приложение задеплоено и сертификат валиден, — единственный порядок, который работает.

## Что получили в итоге

В конце этого этапа нет ни одной настоящей продуктовой фичи — и это ожидаемо. Что есть — это фундамент, на котором будет построен весь фронтенд: пустое-но-деплоящееся Nuxt-приложение, собственный CI-пайплайн, толкающий его на сервер, обратный прокси nginx, терминирующий TLS, бесплатный самообновляющийся сертификат Let's Encrypt и регистрация Mini App, которая заставляет всё это открываться внутри Telegram одним нажатием. Инфраструктура, которая боту была не нужна — HTTPS, домен, прокси, — теперь стоит, и всё, что веб-приложение получит дальше, грузится через неё.

Стоит заметить, насколько этот этап был про эксплуатацию, а не про код приложения. Такова природа веб-фронтенда, которому надо жить внутри Telegram: жёсткое требование — не собрать страницу, а сделать страницу достижимой, безопасно, по реальному адресу. Сделав это один раз, делать заново не приходится.
