> **Architecture First: как в одиночку с ИИ сделать альтернативу Jira** — Часть 14.
> [Предыдущая статья](telegram-login-widget-dotnet-auth) — о том, как веб-версия получила собственный логин и вышла к пользователям. Эта выросла из нашего личного использования продукта — и интересная её часть про добавление обязательного внешнего ключа в таблицу, в которой уже были реальные строки.

Мы — и разработчики, и одни из самых активных пользователей Laraue Boards, — довольно быстро обнаружили ограничение. Эпиков не хватало, чтобы разделить issues: личные эпики оказывались рядом с рабочими, и над ними не было уровня, который держал бы их порознь.

Решение — добавить ещё один уровень в иерархию: **спейс**, группу эпиков, относящихся к одному проекту. Модель данных стала `Space → Epic → Status → Issue` вместо `Epic → Status → Issue`. Мотивация простая; миграция — нет. В таблице эпиков уже были реальные строки, а `SpaceId` должен быть обязательным: эпик без спейса воссоздал бы ровно ту бесхозную ситуацию, от которой спейсы и призваны защитить. Обязательную колонку нельзя добавить в заполненную таблицу за один шаг. Статья в основном про то, как мы это обошли.

## Модель Space

Спейс группирует эпики. Он стоит наверху иерархии и принадлежит пользователю:

```csharp
public class Space
{
    public long Id { get; set; }

    [MaxLength(128)]
    public required string Name { get; set; }

    public Guid UserId { get; set; }

    public bool IsDefault { get; set; }

    public IList<Epic>? Epics { get; set; }
    // ... временные метки
}
```

Флаг `IsDefault` помечает спейс, который создаётся автоматически при создании аккаунта. Логика та же, что у [дефолтного эпика](issue-board-telegram-mini-app) уровнем ниже: вместо nullable `EpicId` на статусе эпики принадлежат реальному спейсу; вместо nullable `SpaceId` на эпике у каждого пользователя есть реальный дефолтный спейс. Модель не допускает бесхозного эпика — просто понадобилось две итерации, чтобы к этому прийти.

`Space` связан с `Epic` через `SpaceId`, который теперь есть у каждого эпика:

```csharp
public class Epic
{
    public long Id { get; set; }
    // ...
    public long SpaceId { get; set; }
    public Space? Space { get; set; }

    public bool IsDefault { get; set; }
    // ...
}
```

## Дефолтный спейс и куда попадает сохранённое сообщение

Дефолтный спейс создаётся при первом обращении пользователя к API — боте, Mini App или веб-версии, что бы ни пришло первым. В этот момент пользователь получает дефолтный спейс, а внутри него — дефолтный эпик и статус, которые уже существовали. Создание живёт в одном месте, так что у пользователя не может оказаться эпиков без спейса.

Именно это и держит работу сохранения сообщений. `GetStatusIdToSaveMessage` разрешает цепочку для новой карточки: пользователь → дефолтный спейс → дефолтный эпик → дефолтный статус. Поскольку дефолтный спейс гарантированно существует с первого обращения, цепочка никогда не обрывается.

## Проблема миграции: добавляем SpaceId в таблицу с существующими строками

[Миграция `CreateSpaces`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.DataAccess/Migrations/20260413113436_CreateSpaces.cs) создаёт таблицу `spaces`. В ней же колонка `space_id` появляется в таблице `epics` — но в этот момент она **nullable**. Другого варианта нет: в таблице уже есть строки, а ненулевая колонка без дефолтного значения отклоняется базой.

```csharp
migrationBuilder.AddColumn<long>(
    name: "space_id",
    table: "epics",
    nullable: true);
```

С nullable-колонкой приложение может начать создавать реальные спейсы и назначать им эпики. Новые эпики сразу получают реальный `SpaceId`. Старые эпики пока хранят `null` — они в переходном состоянии, и это нормально, пока код не читает их, ожидая ненулевой спейс.

## Бэкфилл: вставляем дефолтный спейс для каждого пользователя

Следующий шаг — дать каждому существующему пользователю спейс, чтобы было куда прописать его эпики. Это нельзя выразить как операцию со схемой — это логика над данными, и она идёт в миграцию сырым SQL:

```sql
INSERT INTO spaces (name, color, creator_id, created_at, updated_at, is_default)
SELECT 'Default Space', '#50b3b3', u.id, u.created_at, u.created_at, true
FROM users u;
```

По одному дефолтному спейсу на пользователя, с временными метками из `created_at` самого пользователя. После выполнения у каждого пользователя есть ровно один спейс с `is_default = true`.

Затем существующие эпики прописываются в дефолтный спейс их владельца:

```sql
UPDATE epics e
SET space_id = s.id
FROM spaces s
WHERE s.creator_id = e.user_id
  AND s.is_default = true;
```

После этого у каждого эпика есть `space_id`. Колонка по-прежнему nullable в схеме — база этого не знает, — но ни одна строка больше не хранит `null`.

## Делаем колонку ненулевой

В следующей миграции колонка становится обязательной и добавляется ограничение внешнего ключа:

```csharp
migrationBuilder.AlterColumn<long>(
    name: "space_id",
    table: "epics",
    nullable: false);

migrationBuilder.AddForeignKey(
    name: "fk_epics_spaces_space_id",
    table: "epics",
    column: "space_id",
    principalTable: "spaces",
    principalColumn: "id",
    onDelete: ReferentialAction.Cascade);
```

С этого момента схема обеспечивает то, что приложение и так гарантировало: эпик без спейса не может существовать.

## Почему понадобилось две миграции, а не одна

Бэкфилл и ужесточение колонки попали в более позднюю миграцию, а не в `CreateSpaces`. Это не было осознанным планированием — так отразился реальный порядок событий. Таблица спейсов вышла сначала, с nullable `SpaceId`, пока дорабатывалась логика создания дефолтного спейса при первом обращении. Когда она была готова и протестирована, бэкфилл и ужесточение вошли вместе в следующую миграцию, затронувшую эту часть схемы.

Это распространённый практический паттерн, и его стоит назвать прямо: **три шага добавления обязательного FK в заполненную таблицу — nullable-колонка, бэкфилл данных, ужесточение до ненулевой — не обязаны попасть в одну миграцию.** Важно только, чтобы они шли по порядку. Разбить их по миграциям — нормально, если приложение корректно обрабатывает переходное состояние (nullable-колонка, часть строк ещё без значения). У нас это работало, потому что код, читающий эпики, начал фильтровать по спейсу только после применения бэкфилла.

Сырой SQL в миграции нарушает обычное правило держать миграции чисто декларативными, но здесь это правильный выбор. EF Core генерирует операции со схемой; логику того, какой спейс достанется какому пользователю, знаем только мы. Когда операция над схемой зависит от логики над данными, чтобы быть валидной, эта логика идёт в миграцию.

## Доступ: пользователь видит issues из своих спейсов

С появлением спейсов в модели смысл «доступного пользователю» сдвигается на уровень вниз, но остаётся простым. Все issues пользователя живут в одном из его спейсов, поэтому [`AccessService`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.Services/AccessService.cs) фильтрует по принадлежности к спейсу, а не по прямому владению. Поскольку каждая issue добирается до спейса через эпик, проверять нужно один путь. Общих спейсов пока нет — каждый спейс принадлежит одному пользователю.

## Итоги

Иерархия получила новый уровень: `Space → Epic → Status → Issue`. Дефолтный спейс создаётся при первом обращении к API, поэтому обязательный `SpaceId` для новых данных всегда имеет куда указать. Для существующих данных миграция сделала это в три шага: сначала nullable-колонка, затем бэкфилл сырым SQL, затем ужесточение колонки до обязательной в следующей миграции. Бэкфилл прошёл по каждому существующему пользователю и дал каждому дефолтный спейс.

## Что дальше

Сегодня спейсы принадлежат одному пользователю. Сделать их общими — более крупное изменение: оно затронет доступ, владение и предположения, зашитые во все сервисы, читающие эпики.
