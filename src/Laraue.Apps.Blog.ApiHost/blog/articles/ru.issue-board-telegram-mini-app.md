> **Architecture First: как в одиночку с ИИ сделать альтернативу Jira** — Часть 9.
> [Предыдущая статья](telegram-mini-app-authentication-dotnet) дала веб-приложению настоящий, аутентифицированный бэкенд. С этим фундаментом на месте эта статья строит первое, что приложение реально делает, — и упирается в решение по проектированию БД, которое стоит принять правильно.

Эта статья строит первую настоящую доменную фичу веб-приложения: слой issue — ту часть, что показывает задачи, которые пользователь захватил, и даёт управлять ими на доске. Но читать стоит не ради CRUD-эндпоинтов или Vue-компонентов — а ради небольшого решения по моделированию в середине всего этого, которое мы поначалу приняли неверно и с которым столкнётся каждый, кто строит похожую фичу.

Решение такое: issue группируются в эпики, и часть issue не принадлежит ни одному эпику — они лежат в бэклоге. Как смоделировать «не принадлежит ни одному эпику»? Очевидный ответ — nullable внешний ключ: `EpicId` либо задан, либо `null` для бэклога. Этот ответ ошибочен достаточно часто, чтобы заслужить целую статью, а лучший — смоделировать пустое состояние настоящей строкой-«по умолчанию», а не через `null` — и есть то, что стоит вынести из этой части разработки. Сама фича — это декорации; вот это решение — суть.

## Что такое issue

Issue — это то, ради чего весь продукт: захваченная задача. Это та же единица, которую бот сохраняет, когда приходит сообщение, теперь вынесенная в веб-приложение для управления. Модель маленькая:

```csharp
public class Issue
{
    public long Id { get; set; }

    [MaxLength(4096)]
    public required string? Content { get; set; }

    public DateTime CreatedAt { get; set; }
    public DateTime UpdatedAt { get; set; }

    public Guid UserId { get; set; }
    public User? User { get; set; }

    public long StatusId { get; set; }
    public Status? Status { get; set; }

    public TelegramMessage? TelegramMessage { get; set; }
    public long? TelegramMessageId { get; set; }
    // ... нумерация, кастомные атрибуты
}
```

Контент, временные метки и владелец `UserId` ожидаемы. Связь, которая здесь важнее всего, — это `StatusId`: у issue всегда есть статус, и именно статус связывает её со всем, что выше. `Status` — это одна колонка на доске:

```csharp
public class Status
{
    public long Id { get; set; }

    [MaxLength(128)]
    public string Name { get; set; } = string.Empty;

    [MaxLength(7)]
    public string Color { get; set; } = string.Empty;

    public long EpicId { get; set; }
    public Epic? Epic { get; set; }

    public int SortOrder { get; set; }

    public IList<Issue>? Issues { get; set; }
}
```

А статус принадлежит эпику — через `EpicId`. То есть цепочка такая: `Issue → Status → Epic`: issue не ссылается на свой эпик напрямую — она добирается до него через статус. Эта косвенность сама по себе решение, заслуживающее секунды внимания, и она подводит к решению покрупнее.

## Решение: nullable внешний ключ или отдельная строка?

Это то самое решение по моделированию, обещанное во вступлении, возможно, оно сэкономит кому-то время.

Issue группируются в эпики — более крупные единицы работы, — а колонки доски (статусы) принадлежат эпику. Большинство issue живут в каком-то эпике; остальные лежат в бэклоге, не принадлежа ни одному. Значит, схема должна как-то представлять «эта issue не принадлежит ни одному эпику», и сделать это можно двумя способами.

**Очевидный способ: nullable внешний ключ.** Дать issue поле `EpicId`, которое либо задано, либо `null`, и пусть `null` означает «бэклог». Это естественный первый выбор — и тот, с которого мы начали, — потому что он напрямую ложится на то, как вы об этом думаете: у issue либо есть эпик, либо нет.

Хлопот это принесло больше, чем сэкономило, и причина хорошо обобщается далеко за пределы этого приложения. Nullable внешний ключ, *несущий смысл*, — где `null` означает не «неизвестно» или «ещё не задано», а конкретно «бэклог», — превращает этот смысл в особый случай, который каждый кусок кода обязан помнить. В запросах вырастают ветки `WHERE EpicId IS NULL OR …`. Код приложения снова и снова спрашивает «это null, и если да, считать ли это бэклогом». А вопросы, у которых должен быть один однородный ответ — *к какой доске относится эта issue? к какому пространству? какой набор статусов применим?* — перестают его иметь, потому что для issue из бэклога связь, которая дала бы ответ, по проекту отсутствует. По мере роста модели каждая новая фича, касавшаяся issue, вынуждена была заново обрабатывать null-случай, и цена накапливалась.

Есть и вторая, более острая проблема: бэклог становится ненастраиваемым. У настоящих эпиков есть имя и цвет, и пользователь может их менять. Бэклогу, который `null`, а не строка, негде всё это хранить — у него не может быть ни имени, ни цвета, потому что нет записи, куда их положить. Как только вы захотите, чтобы бэклог вёл себя как остальные эпики (переименовать его, покрасить, дать ему собственные статусы), у nullable-модели нет ответа. Остаётся либо приделать отдельную таблицу, хранящую те же поля, что уже есть у строки в `epics`, — дублируя сам концепт эпика, — либо смириться с тем, что бэклог навсегда второсортный и ненастраиваемый. И то и другое хуже, чем просто сделать его настоящим эпиком.

**Лучший способ: смоделировать пустое состояние настоящей строкой-«по умолчанию».** Вместо того чтобы `null` означал бэклог, каждый пользователь получает настоящий **дефолтный эпик**, и issue из бэклога принадлежат ему ровно так же, как любая issue принадлежит любому эпику. Именно это кодирует флаг `IsDefault` в модели эпика:

```csharp
public class Epic
{
    public long Id { get; set; }

    [MaxLength(128)]
    public required string Name { get; set; }

    public Guid UserId { get; set; }
    public long SpaceId { get; set; }

    public bool IsDefault { get; set; }
    public IList<Status>? Statuses { get; set; }
    // ... временные метки
}
```

С дефолтным эпиком issue *всегда* разрешается в эпик через свой статус — включая бэклог. Её путь к статусам, к пространству, к владельцу всегда есть и однороден — никаких null-проверок, никакой ветки «если бэклог, то…» нигде. Особый случай исчезает — не потому что его хорошо обработали, а потому что он перестал существовать.

Принцип под этим стоит сформулировать отдельно, потому что он всплывает далеко за пределами эпиков и бэклогов: **nullable-колонка, несущая скрытый смысл, — это обычно недостающая строка, прикинувшаяся пустотой.** Как только `null` начинает *означать что-то конкретное* — категорию по умолчанию, корзину «не назначено», вариант «нет», — этот смысл почти всегда хочет быть настоящей строкой, на которую можно навести внешний ключ, а не отсутствием, которое вы повсюду восстанавливаете в коде. Nullable-вариант выглядит проще на уровне схемы и тихо проталкивает сложность в каждый запрос и каждую следующую фичу. Вариант с отдельной строкой стоит одной строки на пользователя заранее — и навсегда убирает целый класс кода с особыми случаями.

Чтобы было ясно: это не «никогда не делайте внешний ключ nullable». Nullable внешний ключ как раз уместен, когда `null` означает *по-настоящему неизвестно* или *законно опционально* — классический пример: сотрудник, у которого `manager_id` равен `null`, потому что у него нет руководителя, или заказ, которому ещё не назначен курьер. Там `null` означает «нет информации / нет связи» — то, ради чего `null` и нужен. Проблема в другом случае: когда `null` это не «неизвестно», а конкретная именованная вещь, которую приложение обрабатывает особо, — «это бэклог», «это категория по умолчанию». Вот это `null`, протаскивающий контрабандой значение, — а значению место в строке. Тест прост: спросите, что `null` *означает* в вашей колонке. Если ответ «мы не знаем» или «её нет» — nullable нормально. Если ответ — конкретный случай, который ваш код раз за разом разбирает по имени, у вас недостающая строка.

Подход с отдельной строкой тоже не бесплатен, и про его цену стоит сказать честно. Раз бэклог теперь настоящая строка, эта строка обязана существовать у каждого пользователя — и что-то должно гарантировать, что она создаётся. Если пользователь хоть как-то может остаться без дефолтного эпика (пропущенный шаг при регистрации, миграция, которая обошла существующих пользователей, ветка кода, что создаёт пользователя, но забывает про эпик), приложение ломается в местах, которые просто предполагают, что бэклог есть. У nullable-модели такого риска не было, потому что «нет эпика» не требовало никакой подготовки. Так что размен реален: модель с отдельной строкой убирает кучу запросов с особыми случаями, но добавляет обязательство по инициализации, которое нельзя завалить. Здесь это обязательство выполняется при регистрации — дефолтный эпик создаётся в том же шаге первого запуска, что создаёт пользователя (из прошлой статьи), так что к моменту, когда хоть одна issue могла бы появиться, бэклог уже есть. Ключ в том, что создание живёт ровно в одном месте; опасность — позволить ему расползтись по нескольким, где про одно можно забыть.

### Второй размен: избыточность против лишнего join

Цепочка `Issue → Status → Epic` прячет связанное решение. Чтобы найти эпик issue, базе приходится джойнить через статус: `issues → statuses → epics`. Этого join можно было бы избежать, храня `EpicId` ещё и прямо на issue, — тогда был бы один join `issues → epics`, быстрее на чтение.

Загвоздка в том, что хранение и `StatusId`, и `EpicId` на issue дублирует информацию: статус уже знает свой эпик, так что `EpicId` у issue пришлось бы постоянно держать согласованным с эпиком её статуса, иначе данные начнут врать. Это реальная нагрузка на поддержку и реальный источник багов — каждая смена статуса должна была бы ещё не забыть обновить эпик.

Это бытовая версия выбора, который разработчики делают постоянно: оставить просто и корректно — или денормализовать ради производительности. Мы выбрали более простую, неизбыточную модель — добираться до эпика через статус, — потому что на этом масштабе лишний join не стоит ничего измеримого, тогда как дублирующая колонка стоила бы постоянной работы по согласованности и напрашивалась бы на баги. Более быстрый join `issues → epics` становится достоин своих хлопот только тогда, когда есть реальное, измеренное давление на оптимизацию. Начинать с простейшей корректной модели и денормализовать позже, когда что-то этого действительно потребует, — почти всегда верный порядок: избыточную колонку всегда можно добавить, когда понадобится, а вот время, потраченное на отлов багов согласованности, которые вы завели раньше, чем это стало нужно, легко не вернёшь.

## Пишем бэкенд: контроллер, host-сервис, core-сервис

С устоявшейся моделью фича собирается в три слоя, и проще всего увидеть, что делает каждый, проследив за одним запросом сверху вниз. Возьмём «создать issue». Запрос входит на контроллере, проходит через host-сервис и заканчивается в core-сервисе.

Сверху — тонкий [`IssuesController`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.WebApiHost/Controllers/IssuesController.cs). Как и `UserController` из прошлой статьи, сам он почти ничего не делает: это набор эндпоинтов под `[Authorize]`, которые читают аутентифицированного пользователя из `HttpContext.User`, собирают запрос и передают его host-сервису. `GetBoard` возвращает доску, а create/update/delete отображаются на соответствующие методы host-сервиса. Единственная работа контроллера — перевести HTTP в вызов сервиса.

Под ним — **host-сервис**, [`IssuesService`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.WebApiServices/IssuesService.cs):

```csharp
public interface IIssuesService
{
    Task<ColumnIssues[]> GetBoard(
        GetBoardRequest request,
        CancellationToken cancellationToken);

    Task Delete(DeleteIssueRequest request, CancellationToken ct);
    Task<long> Create(CreateIssueRequest request, CancellationToken ct);
    Task Update(UpdateIssueRequest request, CancellationToken ct);

    Task<IssueDetailDto> GetIssue(
        GetIssueRequest request,
        CancellationToken cancellationToken);
}
```

Здесь и происходит работа, которая *не* является сырым изменением данных. `GetBoard` раскладывает issue по колонкам для фронтенда. Методы create/update/delete проверяют, что вызывающий вправе делать то, что просит, открывают транзакцию, если несколько изменений должны быть атомарными, и только потом спускаются в core, чтобы реально поменять данные.

В самом низу — **core-сервис**, [`ICoreIssuesService`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.Services/CoreIssuesService.cs), вся поверхность которого — create, update, delete:

```csharp
public interface ICoreIssuesService
{
    Task<long> Create(
        CreateIssueRequest request,
        CancellationToken cancellationToken);

    Task Update(
        long issueId,
        Action<UpdateSettersBuilder<Issue>> setters,
        CancellationToken cancellationToken);

    Task Delete(
        long id,
        CancellationToken cancellationToken);
}
```

То есть запрос на создание идёт по маршруту контроллер → host-сервис (проверяет права, при необходимости открывает транзакцию) → core-сервис (пишет строку). Каждый слой добавляет ровно один вид работы, а следующий раздел делает это разделение явным.

### Принцип: что каждому слою позволено делать

Разделение между двумя слоями сервисов намеренное, и правило для каждого короткое.

**Core-сервис** меняет данные и больше ничего. Он делает create, update и delete, и это *всё*: он не валидирует, не проверяет права, не открывает транзакции (хотя может требовать, чтобы одна уже была открыта), не решает политику. Это тонкий, переиспользуемый слой, который умеет корректно менять данные. В него ходят и бот, и web API, и ни один не хочет, чтобы core ставил под сомнение намерение вызывающего.

**Host-сервис** владеет всем остальным: валидацией, проверками прав, транзакциями и операциями чтения, заточенными под его поверхность. Это слой, который знает, *кто* спрашивает и *вправе* ли он.

Если сказать прямо: core знает, *как* менять данные; host решает, *вправе* ли конкретный вызывающий и *при каких условиях*. Держать валидацию и права вне core — это ровно то, что позволяет одной и той же core-логике обслуживать и бота, и web API, не заставляя ни одного наследовать правила, предназначенные другому.

### Права: кто к каким issue может прикасаться

Правило прав для этой фичи формулируется просто — **пользователь может читать или менять issue или эпик, только если он его создал**, — но важно, где оно применяется. Оно реализовано в отдельном [`AccessService`](https://github.com/win7user10/Laraue.Apps.Boards/blob/main/src/Laraue.Apps.Boards.Services/AccessService.cs):

```csharp
public interface IAccessService
{
    Task<T> GetAvailableEpics<T>(
        Guid userId,
        Func<IQueryable<Epic>, Task<T>> map,
        CancellationToken cancellationToken);

    Task<T> GetAvailableIssues<T>(
        Guid userId,
        Func<IQueryable<Issue>, Task<T>> map,
        CancellationToken cancellationToken);

    Task<bool> CanMoveToStatus(
        Guid userId, long statusId, CancellationToken cancellationToken);

    Task<bool> CanModifyStatus(
        Guid userId, long statusId, CancellationToken cancellationToken);
}
```

`AccessService` сам по себе *core*-сервис — он лежит в том же слое, что и остальные core-сервисы, и вызывается *из* host-сервисов. Его задача — вернуть запрос, ограниченный одним пользователем. `GetAvailableEpics` и `GetAvailableIssues` не возвращают данные напрямую — они принимают `userId` и функцию `map` и отдают этой функции запрос, *уже отфильтрованный до того, что пользователю позволено видеть*. Host-сервис передаёт то, что хочет сделать с этим ограниченным запросом (посчитать, спроецировать, достать одну строку), а access-сервис гарантирует, что тот сможет работать только над записями самого пользователя. Права обеспечены по построению: получить `IQueryable<Issue>`, включающий чужие issue, попросту нельзя.

Host-сервисы опираются на это в своих проверках прав — вместо того чтобы достать issue и потом спросить «а это принадлежит вызывающему?», они стартуют с `GetAvailableIssues` и в принципе видят только свои. Так что права — не отдельный шаг валидации, который можно забыть; это единственный запрос, который host вообще получает.

Держать ограничение доступа в core-сервисе вот так, а не зашивать его в глобальный фильтр запросов или в контроллер, — намеренный выбор с прицелом на будущее. Не каждый вызывающий — аутентифицированный пользователь. Позже могут появиться фоновые задачи, шедулеры или внутренние процессы, которым нужно работать с issue вообще без пользователя в контексте, — и их *нельзя* прогонять через ограничение по пользователю, потому что ограничивать не по кому. Поскольку ограничение доступа — это явный сервис, который host *сам решает* вызвать с `userId`, задача без пользователя просто его не вызывает и работает над всеми данными, какие ей нужны. Правило сегодня — «только создатель»; когда позже в цикле появятся организации, поменяется только реализация этого сервиса — а каждый вызывающий, который им пользуется, продолжит работать без изменений.

### Остальные сервисы устроены так же

Issue — рабочий пример, но у эпиков и статусов свои host- и core-сервисы, построенные ровно по тому же паттерну: core-сервис, который только меняет данные, и host-сервис, который валидирует, проверяет права через access-сервис и управляет транзакциями. Как только форма задана на issue, остальной домен — это «то же самое ещё раз», в чём и смысл иметь форму. Разбирать каждый по отдельности толку мало: они отличаются полями, а не структурой.

### Транзакции: открываются во внешнем слое

Одну деталь в host-слое стоит выделить, потому что это место легко переусложнить: транзакцией владеет *самый внешний* вызывающий — только та сторона, что затеяла всю операцию, должна решать, когда она полностью завершена и готова к коммиту.

Причина в том, что операции компонуются. Host-метод может вызвать другой host-метод, тот — сервис, который делает несколько записей, — и если бы каждый уровень наивно открывал и коммитил свою транзакцию, внутренний шаг мог бы закоммитить (или откатить) половину операции, посреди которой внешний вызывающий ещё находится. Хуже того, у вас были бы транзакции, вложенные в транзакции, а это поддерживает не каждая база. Распространённое, но тяжёлое решение — счётчик на уровне приложения: считать, сколько «begin transaction» в работе, и реально коммитить только когда завершается самый внешний. Это работает, но добавляет машинерию и делает код труднее для понимания — каждый знающий о транзакциях метод обязан участвовать в этом учёте.

Подход здесь проще: самая внешняя операция владеет транзакцией, а внутренние операции просто выполняются внутри той транзакции, что уже активна. Они не коммитят; это оставлено вызывающему, который всё затеял. Но есть реальная тонкость — иногда внутреннему сервису транзакция и правда *нужна*, потому что он пишет в несколько таблиц, и эти записи должны быть атомарными независимо от того, кто его вызвал. Он не может рассчитывать, что вызывающий уже открыл транзакцию. Для этого и нужен хелпер `EnsureTransaction`: он присоединяется к уже идущей транзакции, если она есть, и открывает новую, только если её нет. Так что сервис, которому нужна атомарность, получает её в любом случае, ни разу не открывая вторую, вложенную транзакцию. Правило остаётся чистым — внешний вызывающий решает, когда операция завершена, — а внутренние сервисы, которым нужна собственная страховка, всё равно её получают.

## Рендерим issue: от HTML-прототипа к Vue-компонентам

Когда API на месте, фронтенд может показывать настоящие данные. Визуальный дизайн не нов — он восходит к прототипу из [начала цикла](prototyping-ui-with-ai-before-code), чистому HTML-макету, собранному ещё до того, как появился хоть какой-то реальный код. Этот прототип всегда задумывался как будущие настоящие компоненты; вот здесь он ими и становится.

Короткая ремарка о том, как плоский HTML превращается в Vue-компоненты, — потому что это не та область, где у нас есть продакшен-опыт с Vue или хоть какие-то претензии на best practices. ИИ может разбить всё сам — отдай ему разметку, и он с радостью предложит дерево компонентов. Мы же в основном делали это вручную: смотрели на сгенерированную разметку и резали по повторениям — или просили ИИ сделать *один* компонент из конкретного переданного куска кода. Если один и тот же блок `<div class="card">` повторяется для каждой issue — это компонент `Card`; повторяющаяся обёртка колонки — `Column`. Структура HTML сама подсказывает границы: где кусок повторяется или имеет ясную единственную ответственность, там он и становится отдельным компонентом.

Причина делать это по кусочку, а не отдавать ИИ генерацию всего дерева компонентов разом, — контроль над процессом. Сгенерировать всё сразу — значит получить большой pull request, который придётся ревьюить целиком в конце, где трудно понять, что изменилось и почему. Сборка по одному компоненту держит каждый шаг маленьким и обозримым и оставляет последовательность разработки в руках — что нам важнее, чем сэкономить несколько минут, дав модели сделать всё за один присест. Что в итоге получилось — можно посмотреть в [папке компонентов](https://github.com/win7user10/laraue-boards/tree/master/app/components).

### Разговор с API: клиенты, написанные руками

Каждая область API получает небольшой composable-клиент на фронте, в том же стиле, что и `userApi` из прошлой статьи. У эпиков — [`epicsApi.ts`](https://github.com/win7user10/laraue-boards/blob/master/app/composables/epicsApi.ts), у issue свой, и так далее — каждый это тонкий набор типизированных функций, которые дёргают эндпоинты через аутентифицированный клиент.

Мы пишем их руками. Это стоит отметить, потому что вариант не единственный: при правильно настроенном документе OpenAPI/Swagger на бэкенде эти клиенты можно *генерировать* из определения API, так что типы и вызовы фронтенда автоматически держатся в синхроне с бэкендом. Здесь мы написали их вручную — на таком размере это несложно и избавляет от возни с правильной настройкой генерации из Swagger, — но для API покрупнее или для команды генерация клиента из Swagger обычно более выгодный размен. Это из тех вещей, что нормально делать руками, пока API не станет достаточно большим, чтобы ручная поддержка превратилась в бутылочное горлышко.

### Вписываемся в рамку Telegram: applyInsets

Одна специфичная для Mini App деталь застала нас врасплох, и ею стоит поделиться. Telegram Mini App не получает весь экран — оно рендерится внутри собственной рамки Telegram, и элементы управления Telegram (шапка, кнопки, зона свайпа вниз) перекрывают края веб-вью. Если сверстать приложение так, будто оно владеет всем вьюпортом, эти элементы накроют ваш интерфейс.

Telegram отдаёт *insets* — отступы безопасной зоны, описывающие, сколько места его собственный UI занимает по краям, — и приложение применяет их в [`app.vue`](https://github.com/win7user10/laraue-boards/blob/master/app/app.vue) через шаг `applyInsets`, добавляя layout'у внутренние отступы, чтобы контент сидел внутри рамки, а не под элементами Telegram.

Честная часть в том, что одни insets проблему не решают полностью. Применённые наивно, они могут перестараться — где-то получаешь большие пустые зазоры между приложением и рамкой Telegram, и *при этом* в других местах элементы всё равно подрезаются контролами Telegram, потому что insets не идеально описывают хром каждого клиента. Поймать баланс — это искусство компромисса: добавить отступа достаточно, чтобы избежать перекрытия, но не настолько, чтобы интерфейс плавал в море пустоты. Иногда лучший ход — вообще определить, что приложение запущено внутри Telegram, и подправить CSS специально под случай Mini App — более плотный layout, рассчитанный на рамку Telegram, — а не пытаться одним layout'ом обслужить и обычный браузер, и Mini App.

Практическая рекомендация: отлаживайте эту часть локально, против настоящего клиента Telegram, и запаситесь терпением. Единого чистого ответа нет; это въедливая, попиксельная работа над UI под конкретные платформы, и может уйти много попыток, прежде чем layout начнёт выглядеть правильно во всех клиентах, что вам важны. Быстро итерироваться на своей машине (это позволяет связка с ngrok из прошлой статьи) куда лучше, чем обнаруживать проблемы с перекрытием уже после деплоя.

## К чему мы пришли

Веб-приложение теперь делает что-то настоящее. Оно показывает issue пользователя, разложенные по доске, подтянутые вживую с аутентифицированного бэкенда, — первая реальная фича в продукте, который до этого был чистой обвязкой. Issue можно создавать, двигать между статусами и удалять, и каждое изменение проверяется так, что пользователь всегда трогает только свои данные. Половина продукта про захват (бот) и половина про управление (веб-приложение) теперь обе реальны.

Эта статья намеренно не разбирала построчную реализацию CRUD — тела методов, request-DTO, конкретный LINQ. Весь этот код есть в репозиториях ([бэкенд](https://github.com/win7user10/Laraue.Apps.Boards), [фронтенд](https://github.com/win7user10/laraue-boards)) для всех, кто захочет его прочитать; воспроизводить его здесь значило бы похоронить части, которые реально несут урок, под кучей рутинной обвязки. Структура и решения — вот переносимая часть; а CRUD — это просто CRUD.

Раз появилась настоящая, пригодная к использованию фича, настало время сделать то, что мы откладывали: показать приложение людям и получить честную реакцию. Продукт, которого касался только его автор, не говорит тебе ничего. Так что мы начали выносить его наружу — рассказали о нём в своих Telegram-каналах, написали короткую презентацию продукта в Threads для людей, которые о нём никогда не слышали, и отправили личные сообщения друзьям с просьбой реально попробовать. Цель была не в аплодисментах; цель — посмотреть, как настоящие люди пользуются этой штукой, и выяснить, где она держится, а где нет. Эта обратная связь в итоге значила больше, чем любая фича, которую мы могли бы построить следующей, — чему и посвящена следующая статья.

Но главное, что стоит вынести из этой статьи, — не фича, а решение по моделированию в её центре: когда колонка начинает что-то *означать* тем, что она `null`, этот смысл обычно хочет быть настоящей строкой-«по умолчанию». Бэклог как дефолтный эпик, а не nullable внешний ключ, — один пример выбора, который всплывает постоянно, и если принять его верно, целый класс кода с особыми случаями исчезает прежде, чем успеет накопиться.
